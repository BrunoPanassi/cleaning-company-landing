---
title: 'The good and old legacy code'
description: 'What can be learned and extracted from projects like that'
date: '2026-04-05'
type: 'Toughts'
---

I've seen people hesitant to work with legacy code, often fearing encountering code that is unfriendly and impossible to understand.

Up to that point, I understand and know what it's like to work on a project as if it were a minefield, in addition to the feeling that the system will cease to be useful because it's impossible to maintain.

Because a system that can't be read, can't be maintained, and if it can't be maintained, then it can't be used.

But when you have the pleasure of a challenge where it's possible to improve the code and, in addition to making the system useful again, also make it robust and performant, your perspective on legacy code changes.

And I strongly believe that in the future, those who are skilled in maintaining legacy code will have a great advantage (not just as they already do today), because if there are projects where code is generated much faster, what is the prediction for the readability of that project in a few years?
